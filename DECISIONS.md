## Defense topics (CHALLENGE.md)

All eight are decided below. Observations from the seed data are recorded with them so the answers stay grounded.

**D1. Schema modeling** — decided (mine, via the recommended options except where noted)
- **Average rating: derived.** Computed from reviews with a queryset annotation (`Avg`, `Count`). WordPress's stored ACF value is not imported. Reason: the stored values disagree with the real reviews for 4 of 5 brands (e.g. 3.9 vs 3.08), and the WP theme shows the stored value beside the real review count. Cost: sort/filter by rating is an aggregate; fine at 5 brands. Scaling path is cached columns maintained on review save, not a different source of truth.
- **Reviewers: a `Reviewer` profile in the main app** (`display_name`, `wp_id`, nullable `auth_user_id`). Review FKs to it and keeps its own `reviewer_location` (location varies per review, so it is not a user attribute). The main app stores no passwords or roles; identity lives in the auth service and the link is an opaque id. Only users who authored reviews become Reviewers (8 of 9; the WP admin did not).
- **Industry: ManyToMany** (my choice, over the recommended ForeignKey), faithful to WP's non-hierarchical taxonomy. Consequences to handle: the API returns industries as a list, and the industry filter must `distinct()` to avoid duplicate brand rows. The seed data has exactly one term per brand, so the card can show the first.
- **One description, not two (changed after the first build).** WordPress has a single body per brand and an empty `post_excerpt`, so the first build invented a second stored field, `short_description`. It is gone: `Brand.description` is the only text, sanitized HTML. The card (server-rendered and React) shows an *excerpt* of it, the first 25 words as plain text. The API's `short_description` became `excerpt` (list rows) and `PATCH` now edits `description`, which `GET /api/brands/<slug>/` also returns. The migration (`0003`) drops `short_description` and **discards any text written to it**; descriptions are untouched.

**D2. Postmeta strategy** — decided (mine)
- First-class columns: `website_url`, `founded_year`, `headquarters` (Brand); `rating`, `reviewer_location` (Review); `reviewer_name` becomes `Reviewer.display_name`; `brand` becomes an FK.
- JSON: the two Yoast keys (`_yoast_wpseo_title`, `_yoast_wpseo_metadesc`) in `Brand.seo`. Out of scope for rendering, but the data survives without adding columns.
- Not imported: the ACF `average_rating`, which disagrees with the reviews for 4 of 5 brands (see D1).
- Dropped: ACF `_field_key` reference rows (about half of all postmeta), `wp_yoast_indexable*`, `wp_comments`, WP bookkeeping columns (guid, menu_order, ping status, ...), the sample post, the static pages and the draft page, the `Uncategorized` category.
- Real data is smaller than the "~30 fields" in the challenge: per brand 4 ACF + 2 Yoast keys, per review 4 ACF keys.

**D3. Migration approach** — decided (mine; source and deletion policy accepted as proposed)
- **Source (decided): direct MariaDB.** `manage.py import_wordpress` queries the `wp-db` container. REST can't supply user emails or hashes and returns ACF `brand` as a post id to remap anyway; parsing `dump.sql` means maintaining an escaping-aware SQL parser. (I later built that parser and it was a modest ~250 lines that reproduced the MariaDB results exactly, so the cost was smaller than I said here; the author still preferred the database route. See "migration code isolated" below.)
- **Shape:** one transaction; order industries, brands (+ industry links), reviewers, reviews; `update_or_create(wp_id=...)` everywhere; `--dry-run` and a created/updated/unchanged summary; HTML sanitized on import; ACF `_field_key` rows skipped. `short_description` is set only on create so editor PATCHes survive re-runs. Slugs follow WP on update so permalinks stay matched.
- **Deletions (decided):** additive by default (a bad read can't wipe data); optional `--prune` after a dry-run report.
- **User link (decided): UUIDv5 bridge.** Migrated users get `id = uuid5(NAMESPACE, wp_id)` in the auth service and the same value in `Reviewer.auth_user_id`; users created later get random `uuid4`. Determinism exists only so two independent importers agree without a cross-service call; it is not the id scheme for new users (a native reviewer later would be `get_or_create(auth_user_id=<token sub>)`). Costs: mixed id provenance (needs a README note), the namespace constant is needed by both importers (placement is a D8 question), and the auth user still stores a nullable `wp_id` for importer idempotency. Rejected: auth lookup by `wp_id` (couples the importers, needs a migration-only endpoint) and reusing the WP integer id (leaks WP's scheme).
- **Scale to 100x:** `bulk_create`/`bulk_update` in chunks, prefetch `wp_id` to pk maps once, stream the source reads, and a `post_modified` watermark so re-runs touch only changed rows. Not built at this size; documented as the path.

- **Implemented (`services/app/catalog/management/commands/wp_migration/`):** `source.py` (a `WordPressSource` protocol plus `MariaDBSource`), `importer.py`, `sanitize.py` (nh3 allowlist), command `import_wordpress [--dry-run] [--prune]`. Importer logic is tested against an in-memory fake source; three integration tests run against the real `wp-db` data and skip when it is not up.
- **No shared model base class:** the `wp_id`, `created_at` and `updated_at` fields are declared directly on each of the five models (the abstract `WPSourced` base was removed at the author's request). They sit first in each model, in the same order the base class gave them, and the migration autodetector reports no change.
- **Behavior I chose while building (not in the decision above):** a dry run does the full import and rolls back, so its counts equal a real run. `--prune` refuses (exit with an error) when the source returns zero rows for a model that has imported data locally, since that looks like a bad read; the cost is that deleting every review in WordPress needs a manual cleanup. Rows created natively (no `wp_id`) are never pruned. Reviews with an invalid rating or an unknown brand are skipped and reported. A review's `reviewer_name` that differs from the author's display name is reported once; the display name wins. Only users who authored an imported review become Reviewers. Rows are written one at a time, with `wp_id` maps prefetched once; bulk writes remain the documented scaling path.

**D4. API contract** — decided (mine)
- **Endpoint:** `GET /api/brands/?industry=<slug>&industry=<slug>&ordering=-average_rating&page=2&page_size=12`.
- **Pagination (decided): page number**, DRF's `{count, next, previous, results}`. Supports "page X of Y" and trivial URL sync; offset drift is a non-issue for a near-static list. A mobile client with an infinite-scroll feed would be the reason to add cursor pagination later.
- **Sort param (decided): `ordering`** with a leading `-` for descending; allowed `name` (default), `average_rating`, `review_count`. Unreviewed brands sort last on rating.
- **Row shape:** `name, slug, industries[{name, slug}], average_rating (1 dp, null if no reviews), review_count, excerpt, top_review{slug, title, rating, snippet, reviewer} | null`. `industries` is a list because of the M2M decision (D1); the spec says "industry".
- **Filter:** repeatable slug param, OR across values; unknown slug returns an empty page (stale bookmarks degrade gracefully). Implemented with an `Exists` subquery, not a join, so the review count is not inflated.
- **"Top review" (decided):** highest `rating`, then most recent `published_at`, then highest `id`. Snippet is the body with HTML stripped, truncated to about 140 characters at a word boundary. WP has no such concept (the theme's brand cards show only an excerpt of the brand body, the brand page lists reviews newest first), so this is new behavior. Known bias to state in the README: it skews positive, and since all seeded reviews share one date the `id` tie-break decides among equal ratings.

**D5. Component & state** — decided (mine; URL sync, loading UX and mounting took the recommended options)
- **Server state: TanStack Query** (my choice, over the recommended hand-rolled hook). Gives caching, request dedup, cancellation via the `AbortSignal` passed to the query function, and `placeholderData: keepPreviousData`. Costs a dependency whose behavior I must be able to explain: query keys are the normalized URL params, retries apply to network/5xx errors only (not 4xx), and `staleTime` is a deliberate value rather than the default of 0.
- **UI state lives in the URL, not in component state.** Filters, sort and page are the query string (`industry`, `ordering`, `page`, named like the API) and the component derives its query from it. Plain History API (`URLSearchParams`, `pushState` on user changes, `popstate` listener); no router, because the component is a single embedded view. Deep links, back/forward and reload all work. Defaults are omitted from the URL; changing a filter resets `page`.
- **Loading/error UX:** first load shows skeleton cards (stable layout); refetches keep the previous results visible, dimmed, with `aria-busy`; errors render inline with a Retry button and keep any previous results; empty state offers "clear filters". The result count is announced through an `aria-live` region.
- **Markup/a11y:** the industry filter is a disclosure button opening a panel of real checkboxes (redesigned from a chip row, see "BrandList toolbar" below), sort is a button opening an ARIA listbox whose options are each a tab stop, as the Industry checkboxes are (Tab and Shift+Tab walk them; arrows, Home/End and type-ahead work too), Enter or Space chooses and closes, tabbing past the last option or Escape closes (it was radio buttons, whose arrow keys choose as they move, so the panel closed on the first arrow press) (it was a native `<select>`, replaced because browsers draw that popup themselves and Chrome's phone emulation draws it detached from the control; both controls now share one open/close hook), results are a real `ul`/`li`.
- **Mounting (S9 resolved):** Vite builds one JS+CSS bundle served as Django static files; a server-rendered `/brands/` page provides `<div id="brand-list">` and loads it. Same-origin API, so no CORS.
**D6. SCSS architecture** — decided (mine; all four took the recommended options)
- **Observations from `theme.css`:** 12 custom properties already exist, but `#ffffff` is hardcoded about 9 times, text greys (`#374151`, `#1f2937`), the footer palette and badge greens are literals, the hero gradient repeats the primary color as a hex, and spacing is ad hoc (15 distinct values). `.card`, `.review-item`, `.brand-body .content` and `.page-body` are the same white bordered surface; `.brand-hero` and `.review-hero` are the same hero. Selectors are descendant-heavy (`.card h3 a`). One breakpoint (640px).
- **Structure: 7-1 style folders** under `services/app/frontend/scss/`: `abstracts/` (tokens, mixins), `base/`, `layout/`, `components/`, `pages/`; `main.scss` contains only `@use` lines. Modern `@use`/`@forward`, no `@import`.
- **Naming: BEM with flat selectors** (`.card`, `.card__title`, `.card--featured`), so specificity stays at one class and no style depends on markup depth. The WP class names are not kept (I write the Django templates, so renaming is free); enforced with a stylelint class-name pattern.
- **Tokens: SCSS maps emit `:root` custom properties** for color, a 4px-based spacing scale, type scale, radii and shadows. Breakpoints stay SCSS-only (custom properties can't be used in media queries). Off-scale values (22px, 18px, 14px, ...) snap to the nearest step, so output is equivalent, not identical. The shared surface/hero patterns are merged into `_surface` and `_hero` components.
- **Delivery: one global stylesheet** compiled by the Sass CLI and served as Django static; server-rendered pages and `<BrandList />` both use it, so card/badge/stars have a single definition. BrandList-specific styles (filters, skeleton, error/empty states) live in the same tree.
- **Verification plan:** a script compiles the SCSS and checks that every rule in `reference/theme.css` has a counterpart (modulo snapped values).
**D7. Service boundary** — decided (mine; all four took the recommended options)
- **Auth service owns:** users (UUID id, username, email, password hash), roles (`reader`, `editor`) and who holds them, login, refresh tokens, signing keys, disabling users. **Main app owns:** domain data, the `Reviewer` link (opaque `auth_user_id`), and enforcing what each role may do on its endpoints. It stores no passwords, credentials or roles and never mints tokens.
- **Auth endpoints:** `POST /api/auth/token/`, `POST /api/auth/refresh/`, `GET /.well-known/jwks.json`, internal `POST /api/auth/introspect/`.
- **Verification: local JWT.** Access tokens are signed JWTs verified in-process with cached public keys. Claims: `iss`, `aud` (the main app), `sub` (user UUID), `exp`, `iat`, `jti`, `roles`. `iss` and `aud` are checked so a token minted for another service cannot be replayed here.
- **Signing: asymmetric + JWKS.** Auth holds the private key and publishes public keys with `kid`s; the main app can verify but not forge. Rotation: publish the new key alongside the old, switch signing, retire the old after the longest token lifetime. The main app caches JWKS and refetches on an unknown `kid`.
- **Revocation / role change: short TTL + introspection on writes.** Access tokens live about 10 minutes and refresh tokens are revocable, which bounds the window for reads. `PATCH /api/brands/<slug>/` also calls introspection, so revocation and role changes are immediate where it matters, and the role check uses the introspected roles, not the token's.
- **Auth outage:** reads (public) are unaffected. A write with a still-valid token fails closed with 503 when introspection is unreachable (short timeout, no fallback to the token's roles). Local verification keeps working for any endpoint that does not introspect, using cached keys.
- **Authorization: role names** in the token; the shared lib exposes a single `require_role(...)` check, so moving to permission strings later is a local change. Auth owns who has which role, the main app owns what each role may do.
- **Defaults taken while building (implemented, never explicitly confirmed):** the introspection call is authenticated with a service secret from the environment (internal network only); imported WP users get unusable passwords, with a documented dev-only command to set one.

**D8. Shared library** — decided (mine); D8a interpretation awaiting confirmation
- **Modules (each used by both services unless noted):** `claims` (Claims type, claim names, `Role`, `ISSUER`/`AUDIENCE`, per-version encode/decode, so issuer and verifier cannot drift); `verify` (JWT verification, JWKS cache via PyJWT's `PyJWKClient`, `iss`/`aud`/`exp`/`v` checks; main app today, pure Python, deps: `PyJWT[crypto]` only); `drf` (authentication class and `require_role` permission class; main app only, optional extra `ca-authlib[drf]` so auth doesn't install DRF); `ids` (see D8b). Out: login/issuing/signing keys/models/settings (auth only). Tests run without either Django project (plain pytest for the core; the DRF adapter uses a tiny `settings.configure()` fixture).
- **D8a, introspection (interpretation, to confirm):** the introspection *client* stays in the main app and the lib's permission class takes an injectable hook, so the lib stays small. The *authority* over trust stays in auth: what is valid, who holds which role, revocation, and which token versions are live. The request/response schema is part of `claims`. Auth's HTTP API is versioned by path (`/api/auth/v1/...`), and a new version runs alongside the old one until its clients move. Local JWT verification cannot live in the auth service (D7: no per-request call), which is why the lib exists.
- **D8b, `ids` (decided): one definition in the lib** (`user_id_from_wp_id()` plus the UUIDv5 namespace). It is not scheduled for deletion; its docstring says it exists for the WP migration and that a future maintainer may delete it once nothing depends on it. Cost: migration-origin code in a long-lived package.
- **D8c, distribution (decided): workspace for dev, SemVer ranges + git tags.** The lib stays a uv workspace member (editable, so compose bind-mounts give live edits). Each service declares a compatible range (`ca-authlib>=0.1,<0.2`); releases are git tags (`ca-authlib/vX.Y.Z`) with a built wheel, so a service can lag a release. In this repo only the workspace is wired; the README documents the release flow and does not claim a publishing pipeline exists.
- **D8d, breaking token changes (decided): versioned tokens, a `v` claim.** Tokens carry `v` (v1 from the start; a token with no `v` or an unknown `v` is rejected with 401). The lib's `claims` module holds an encoder and a decoder per version. Auth keeps a per-audience setting for which version to issue, so it supports several versions at once and each consumer moves on its own schedule; the verifier takes an `ACCEPTED_TOKEN_VERSIONS` setting. Rollout: (1) release lib N+1 with v1 and v2 parsers; (2) deploy the main app with both accepted; (3) flip the audience's issued version to v2 in auth (rollback is flipping it back); (4) later remove v1. Because access tokens live about 10 minutes and refresh issues new tokens at the current version, a retired version drains within one TTL. Cost: two live parsers during a rollout and a written retirement rule (drop a version when no audience issues it and one TTL has passed).

## Implementation notes: auth service, shared library and the protected endpoint

- **Library (`libs/ca_authlib`, 89 tests, runnable without either service):** `errors`; `claims` (the token contract: `Claims`, `Role`, per-version encode/decode registry, `issue_claims`, the `Introspection` shape); `verify` (`JWKSClient`, `TokenVerifier`); `drf` (`JWTAuthentication`, `require_role`, optional `drf` extra); `ids`; and `testing` (a key pair, JWKS and token-signing helper). Both services import `claims`; the auth service also uses `verify` for its own introspection. **`testing.py` is the one module no service uses at runtime**: it exists so the library, the app and the auth service do not each reimplement token signing in their tests. It is the first thing to move into a separate dev-only package if the library should be strictly runtime code.
- **Signing:** Ed25519 (`EdDSA`). The verifier takes an explicit algorithm allowlist, so `alg: none` and the HS256-with-the-public-key confusion attack are rejected (both tested). Keys live in the auth database (`SigningKey`): the newest unretired key signs, every unretired key is published at `/.well-known/jwks.json`. `rotate_signing_key` adds a key; `rotate_signing_key --retire-old` retires keys that stopped signing more than one access-token lifetime ago. **The private keys are stored unencrypted in the database, which is dev-grade; production would use a KMS or secrets manager.**
- **Key cache behavior (`JWKSClient`):** keys are reused for 300s; an unknown `kid` triggers a refresh (how a rotated-in key is picked up); refresh attempts are at least 30s apart, successful or not, so neither a flood of bad `kid`s nor an outage turns every request into a call to auth; if a refresh fails the cached keys keep being used. Consequence: a retired key can still verify for up to about five minutes after it is retired, and a main app with no cached keys and no auth service answers 503, not 401.
- **Tokens:** access tokens are JWTs with `iss`, `aud`, `sub` (user UUID), `iat`, `exp`, `jti`, `roles` and `v`, valid 10 minutes. A token without `v`, or with a version the service does not accept, is rejected (tested). Auth keeps a per-audience `token_version` (setting `AUDIENCES`, env `AUTH_TOKEN_VERSION_APP`); the main app's accepted versions are `CA_AUTH["ACCEPTED_TOKEN_VERSIONS"]`. **Only v1 exists.** The dispatch is built and tested with a fake v2 (issuer and verifier can move independently), but no real v2 has been written.
- **Refresh tokens:** opaque, stored only as a SHA-256 hash, single use (redeeming one revokes it and issues a new pair), 7-day lifetime, and a disabled user cannot refresh. **Not built:** reuse detection (a stolen token used first locks the owner out but does not revoke the rest of its family), a logout endpoint, and login rate limiting, so there is no brute-force protection on `/token/`.
- **Endpoints (versioned in the path, D8a):** `POST /api/auth/v1/token/`, `POST /api/auth/v1/refresh/`, `POST /api/auth/v1/introspect/` (requires the `X-Service-Secret` header), `GET /.well-known/jwks.json`. Bad credentials, a disabled user and an unusable password all return the same 401, and a missing user costs a dummy password check.
- **Introspection:** answers from the database, so a demotion or a disabled user shows up at once. The client lives in the main app (`catalog/auth.py`); the library's `require_role(..., fresh=True)` reaches it through `CA_AUTH["INTROSPECTOR"]`. **Any failure to get a clear answer is a 503, never "inactive" and never "allowed":** a timeout, a 5xx, a rejected service secret (401/403, i.e. misconfiguration) and an unreadable body all fail closed.
- **The write endpoint:** `GET /api/brands/<slug>/` is public; `PATCH` needs the `editor` role and edits only `description` (HTML, up to 20,000 characters sent; cleaned to the allowlist, and a body with no text left after cleaning is a 400). Unknown fields are a 400 rather than silently ignored; a non-string is a 400 (DRF's `CharField` would otherwise turn the number 5 into "5"); `PUT` and `DELETE` are 405. The editor's id is logged; there is no audit table. A malformed or forged bearer token is a 401 even on the public GET, which is DRF's normal behavior.
- **Users:** `import_wordpress_users` creates each WP user with `id = user_id_from_wp_id(wp_id)` (matching the main app's `Reviewer.auth_user_id`), an unusable password, and roles `reader` (plus `editor` for WordPress administrators and editors). Roles and passwords are set only on creation, so a re-run does not undo a grant or revoke made in auth; a changed username or email is updated. **There is no `wp_id` column on users:** a migrated user's id is `uuid5` of the WordPress id, so the id is the import key and the column would only repeat it (dropped in migration `0004`). The main app's models keep `wp_id` because their ids are integers: it is their import key, their link back to WordPress and what `--prune` uses to leave native rows alone. Making every id deterministic was weighed and not done: UUID primary keys for the five models would need a primary-key migration, make the reviews' id tie-break arbitrary, lose the visible WordPress id, and gain only one column. `set_dev_password` sets a password and refuses to run unless `DEBUG` is on. `require_role` checks the exact role, so an editor needs the `editor` role (the importer grants both).
- **Compose:** `app` and `auth` run `migrate` on start. The service secret has a dev default (`dev-service-secret`) in compose and in settings; any real deployment must set `AUTH_SERVICE_SECRET` on both.
- **Verified:** library 89 tests (forged, expired, wrong-audience and wrong-issuer tokens, algorithm confusion, rotation, outage, rate-limited refetch); auth 53 (login, refresh rotation, introspection, key rotation and retirement, the importer including the real WordPress users); app 133 (the PATCH matrix, demotion, outage). `scripts/demo-auth.sh` was run against the live containers: reader 403, editor 200, a demotion refused on the same token, auth stopped gives reads 200 and writes 503.

## Review pass against CHALLENGE.md

Each requirement was checked against the running system rather than the tests alone. Findings and what was done:

- **Accessibility, measured in a real browser.** axe-core (WCAG 2.0/2.1 A and AA plus best-practice rules, so including colour contrast, which jsdom cannot judge) was run in the browser pane on the homepage, `/brand/` (empty and filtered), a brand page, a review page and the real 404 template, at desktop width and at 375px: **zero violations on every page, no horizontal overflow.** (Caveat found later: axe reports text it cannot evaluate as "incomplete" rather than failing it, and I had only read the violations. It could not judge the hero text over the gradient or the star glyphs; both were then checked by computing the WCAG ratios by hand, see "Contrast, checked by hand" below.) A by-hand keyboard pass of `/brand/` confirmed the skip link is the first stop, focus rings are drawn, and Space toggles a filter and updates the URL. This was a one-off manual audit; it is not an automated check. **Still not done: a screen reader.**
- **Hostile input found three 500s and two loose spots, all fixed with regression tests.** `?industry=%00` crashed the unauthenticated listing (Postgres rejects NUL bytes): a value that cannot be a slug is now an unknown industry, an empty page. My own `PATCH` validation crashed on a JSON array of objects or a bare number because the unknown-field check ran before DRF's type check: a non-object body is now a 400. Form-encoded and multipart bodies were accepted: both services are now JSON-only (415 otherwise). `X-Frame-Options: DENY` was missing: added. Credential fields are now length-bounded (username 150, password 1024, tokens 256 and 8192).
- **Consistency check added:** the roles seeded in the auth database must equal the library's `Role` enum (a test).
- **Verified fine:** page size and page number handling (garbage falls back, size capped at 50), 405s, trailing-slash redirects, every malformed auth body (400 or 401, never 500), `X-Content-Type-Options` and `Referrer-Policy`, no secrets, build output or logs would be committed, production JS dependencies have no known vulnerabilities.
- **Accepted:** one high-severity advisory in a dev-only dependency (`braces`, inside stylelint's glob matching) with no patched release. It is build-time only and never shipped.
- **Gaps left, by decision:** no `/industry/<slug>/` archives (the challenge requires only the home, brand and review pages). (The Docker-only gap found here was then fixed, and the `/review/` archive and About page were added afterwards, see below.) A slug containing characters outside `[-a-zA-Z0-9_]` would import but be unreachable (the seed data has none).

## Implementation notes: reusable components and SCSS restructure

A review of the frontend (components, SCSS, and `reference/theme.css`) found generic UI buried under BrandList names; this moves it out.

- **The reference theme:** `reference/theme.css` is flat and markup-coupled: descendant selectors (`.hero h1`, `.card h3 a`), unprefixed class names (`.meta`, `.excerpt`, `.current`), raw px and hex values, one file with comment sections. ## Implementation notes: one description, escaped on cards

- **Cards escape, the brand page renders.** A card shows `excerpt`, plain text derived from the description (tags dropped, entities decoded, first 25 words: `catalog.text.excerpt`). Django auto-escapes it and React renders it as a text node, so markup can never take effect on a card even if unsafe HTML were somehow stored (a test writes it with `update()`, past `save()`, and checks the cards). The brand page is the only place the stored HTML is rendered (`|safe`). **Interpretation to confirm:** escaping the raw HTML would have shown literal `<p>` tags on every card, so tags are stripped first and the remaining text is escaped.
- **Edited descriptions.** With one field, an editor's `PATCH` (or admin edit) and WordPress's body compete for it. The brand keeps `wp_description`, the text last read from WordPress. While `description` still equals it, nobody has edited here and the next import replaces it; once they differ, the import leaves the description alone (and still records WordPress's latest in `wp_description`). So both rules hold: WordPress changes flow in until Django takes over, and an edit survives a re-run. Costs: there is no way to say "discard my edit and take WordPress's" except editing the text back (or clearing `wp_description`); and an edit that happens to equal WordPress's text counts as unedited.
- **Not done:** no HTML-aware length limit (the `PATCH` limit counts the characters sent, before cleaning); the demo-brand script now writes a plain description.

## Implementation notes: admin sites

Added after the original scope: a Django admin with a page for every model in both services (5 in `catalog`, 4 in `accounts`).

**Update, after a practice panel review: the main app's admin was removed** (commit "app: remove the Django admin"). The review's findings: the WordPress admin is out of scope in CHALLENGE.md, and the admin's sign-in kept a staff flag per editor in the main app, a cached role, against D7's "the main app stores no passwords or roles". Removed with it: `catalog/admin.py`, `catalog/admin_auth.py`, the `login()` client, the sessions, messages and CSRF middleware, the `AUTH_TOKEN_URL` setting and the main app's admin tests. Editors change content only through `PATCH /api/brands/<slug>/`. The auth service keeps its admin, where roles are granted and revoked. The notes below are the record of what was built.

- **Decided (the author): the main app's admin signs in through the auth service.** The alternative, local Django superusers, would have put operator passwords in the main app and broken the D7 boundary. Editors type their auth-service username and password into the admin login form; `catalog/admin_auth.py` checks them with the token endpoint (`catalog.auth.login`), verifies the returned token with the shared library, and admits only editors. Django still needs a local user row for the session and the change history, so the app keeps one per admin: username is the auth-service user id, the password is unusable, and the only thing stored is a staff flag re-derived at each sign-in. **So the main app does hold one piece of authorization state, a flag per admin, refreshed at sign-in rather than live.** A demoted editor is refused and their row demoted at their next sign-in attempt (a failed check, such as a wrong password or an outage, never demotes anyone); an existing session lasts at most `SESSION_COOKIE_AGE` (one hour). No row is ever created for a non-editor.
- **Costs of that choice, accepted:** every sign-in also creates a refresh token in the auth service that nothing uses (it expires in 7 days); any failure (wrong password, reader, auth service down, bad token) shows the same "staff account" message; sign-in has no rate limiting (the token endpoint has none either); history entries name the user by their id, with the username in the first-name field.
- **The auth service's admin uses its own users**, with a new `User.is_staff` flag (migration `0003`). There is one level of admin access, so `is_superuser` is a read-only property equal to `is_staff` and `has_perm` is `is_active and is_staff`; that is what lets Django's `UserAdmin` (add user, password change, role picker) work on a model that is not built on `AbstractUser`. `createsuperuser` makes a staff user holding every role. Staff is deliberately not granted by the importer to WordPress administrators: the auth admin can edit users and roles, so it is opt-in.
- **Per model.** `catalog`: industries and reviewers show brand and review counts; brands show the *derived* rating, review count and industries (sortable); reviews filter by rating, brand and date and pick brand and reviewer with search-as-you-type; pages refuse route-shadowing slugs. `accounts`: users with role and staff filters and a "revoke all refresh tokens" action; refresh tokens with a status filter and a revoke action; signing keys with a status column (active, published, retired); roles. **Roles, signing keys and refresh tokens are view-only** (tokens can be revoked or deleted), because roles are a fixed set the shared library defines (a test pins the database to it), keys are rotated by command (retiring the signing key from a form could invalidate live tokens), and a token is never to be written by hand.
- **Secrets never reach a page:** the private key and token hashes are excluded from every field list, and a test searches the rendered HTML for key material.
- **Stored HTML stays sanitized, in the model.** The templates render brand descriptions, review bodies and page bodies with `|safe`, which is only safe if nothing unsafe is ever stored. `Brand.save()`, `Review.save()` and `Page.save()` now run the `nh3` allowlist (`catalog/sanitize.py`), so the importer, the admin, the API and a shell all go through it. The importer and the `PATCH` serializer also sanitize up front (to compare values, and to reject a body that is only unsafe markup). **Not covered:** `QuerySet.update()`, `bulk_create()` and raw SQL skip `save()`; that is why the card never relies on it (below).
- **Admin edits vs. the importer.** `import_wordpress` re-applies WordPress's values (slugs, titles, bodies, ratings, industry links) on every run, so admin edits to imported fields are overwritten by the next import; the exception is a brand's `description`: see "Edited descriptions" below. Each model's Import section says so, and `wp_id` and the reviewer's `auth_user_id` are read-only. Making the admin authoritative (for example by skipping rows edited in Django) is not built.
- **Switched off:** Django's own `User` and `Group` admin in the main app (local passwords and permissions, which this design does not use) and `Group` in the auth service (roles are the mechanism).
- **Bugs and traps found while building:** (1) both services' admins would have shared `sessionid` and `csrftoken` cookies, since browsers share cookies across ports on `localhost`, so each service now names its own (verified in a browser: signing in to one admin leaves the other signed in); (2) annotating a queryset with an aggregate makes Django drop the model's default ordering, so the annotated admins (and the brand autocomplete, which paginates) had no stable order: each now sets an explicit `ordering`; (3) the `FORMS_URLFIELD_ASSUME_HTTPS` setting that silences the Django 6 `URLField` warning is itself deprecated, so the scheme is declared on the form field instead (a website typed as `example.com` becomes `https://example.com`); (4) the auth service had to gain templates, sessions, messages and CSRF middleware for the admin, and DRF views are CSRF-exempt, which a bare `curl` POST to the token endpoint and the whole demo script confirmed still works.
- **Verified:** 45 admin tests in the main app (sign-in success and every failure mode, no password stored, demotion, cookie names, all five models, sanitization, reserved slugs, derived columns, autocomplete, read-only fields, query count) and 32 in the auth service (access control, add and edit users, password change, role editing, actions, read-only models, no key material in any page, `createsuperuser`), plus a missing-migration check in each; run with deprecation warnings as errors. In a real browser: signed in to both admins with real credentials, the brand and review lists (derived ratings shown), the auth users list and signing-key page, and both sessions alive at once.
- **Not built:** admin pages are Django's default look (not the site's SCSS); no two-factor or lockout; no model-level sanitizing; the admin does not show the importer's last run.

## Implementation notes: brands API

- **Built:** `GET /api/brands/` in `catalog/api/` (DRF `ListAPIView`, public). Parameters: `industry` (repeatable slug, OR), `ordering` (`name` default, `average_rating`, `review_count`, `-` to reverse), `page`, `page_size` (default 12, max 50). Response is `{count, next, previous, results}`.
- **Additions to the D4 row shape:** each brand and each top review also carries a relative `url` (`/brand/<slug>/`, `/review/<slug>/`) so a card can link without rebuilding URLs. `average_rating` is a JSON number (1 dp) or null; `snippet` is plain text with entities decoded, so clients must render it as text, never as HTML.
- **Top review in one query:** a `Prefetch` ranks each brand's reviews with `ROW_NUMBER()` over (rating desc, published_at desc, id desc) and keeps rank 1. A request costs 4 queries (count, brands, industries, top reviews) regardless of page size; a test caps it. The listing defers the large `description` and `seo` columns.
- **Filter:** `EXISTS` subquery, not a join, so a brand in several matching industries appears once and its stats are not inflated (tested).
- **Ordering choices beyond D4:** unreviewed brands sort last on rating in *both* directions; `name` then `id` always break ties so paging never repeats or drops a brand (tested with 30 tied brands). An unknown `ordering` field is a **400 with a message**, where DRF's default would silently ignore it: a typo should not quietly return a different order. An unknown `industry` slug is still an empty page (D4).
- **Out-of-range `page` is a 404** (DRF's default `Invalid page.`). The React component has to handle it, for example by dropping back to page 1 for a stale bookmark.
- **Known cost:** the `count` query runs the rating aggregate even though the count does not need it; at much larger scale it would count the filtered brands without the join.
- **Auth settings:** global DRF defaults are no authentication and `AllowAny`; the write endpoint will add token authentication and a role permission per view.

## Implementation notes: SCSS tree

- **Layout built:** `services/app/frontend/scss/` with `abstracts/` (tokens, mixins), `base/`, `layout/`, `components/`; `main.scss` is only `@use` lines. Compile with `make css` (or `pnpm build:css`; `pnpm dev:css` watches) into `services/app/static/css/site.css`, which is git-ignored and must be built before the pages are styled. The `pages/` folder from D6 was **not** created: merging the brand and review heroes and the white panels into `hero--plain` and `surface` left no page-specific styles, and an empty folder would be noise.
- **Tokens as functions:** components call `t.color("text")`, `t.space(6)` and so on, which return `var(--...)` and fail the build on an unknown name, instead of writing raw values. The maps are emitted once as `:root` custom properties by `base/_root.scss`.
- **Where I departed from the reference:** spacing and type snap to the scale (22px/28px panel padding became one 24px step; text greys `#374151` and `#1f2937` merged into `text-soft`); `html` font-size is `100%` instead of a fixed `16px`, so the user's browser setting is respected; added `:focus-visible` outlines and `prefers-reduced-motion` handling, which the reference lacks; the page title is a `<p>`, not an `<h1>` repeated on every page.
- **Desktop-first:** the `below("sm")` mixin (max-width 640px) mirrors the reference's single breakpoint instead of rewriting everything mobile-first.
- **One flat-selector exception:** the hero title size is a custom property (`--hero-title-size`) so a variant or breakpoint can change it without a descendant selector. `.hero--plain` must stay declared after `.hero` because it resets the value the breakpoint sets. `.prose` is the only place child selectors are allowed (stylelint override), because CMS HTML is not ours to add classes to.
- **Enforcement:** stylelint (`standard-scss`) plus a BEM class-name pattern, max one compound selector, no ids, no type selectors outside `base/`. `pnpm lint` runs ESLint and stylelint.
- **Verification:** `scripts/check-parity.mjs` (part of `pnpm test`) compiles the SCSS and checks that each of the 53 mapped rules in the reference CSS has a counterpart setting the same properties (`scripts/parity-map.json`; longhands count as their shorthand), and that every class used in the Django templates has CSS. 10 reference rules are skipped on purpose and listed with reasons in the map (nav, section-header links, footer links, pagination). A copy of the reference stylesheet is committed at `services/app/frontend/reference/theme.css`. Values are not compared, since they snap to the scale.
- **Checked visually** against live WordPress on the homepage, a brand page and a review page at desktop and 375px, with no horizontal overflow on mobile.
